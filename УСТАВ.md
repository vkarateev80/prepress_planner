редакции и ведёт файл; агенты-исполнители устав не правят — предлагают изменения
через ведущего разработчика.

**1.4. Порядок пересмотра.**

| Что | Правило |
|---|---|
| Основание | Изменение границ продукта, архитектурных запретов, критериев готовности или состава ролей |

| Экстренно | Допускается по факту инцидента (безопасность/деньги) с обязательным уведомлением заказчика |

## 2. Миссия и границы продукта

**2.1. Миссия.** «Препресс-Планер» — приложение препресс-планирования расходных
материалов и технико-экономического обоснования (ТЭО) тиражей этикеток: импорт
чертежа → лечение геометрии → распознавание массива → раскрой с рейтингом по
магнитным валам → перебор вариантов → ТЭО → отчёты PDF/XLSX/DXF
(`README.md`:1–5; `docs/HANDOFF.md`, §шапка).

**2.2. Что делаем (в объёме).**

## 4. Роли и ответственность

| Роль | Зона ответственности | Что согласует |
|---|---|---|
| **Заказчик** (владелец продукта) | Границы продукта, приоритеты, деньги, приёмка, утверждение устава; владеет сервером и данными | Всё из §2, тарифы, состав релиза, любые серверные настройки |
| **Ведущий разработчик / агент** | Архитектура, домен, ревью, состояние документации, прогон гейтов, ведение устава и `docs/HANDOFF.md` | Технические решения внутри §5, состав коммитов, порядок работ внутри согласованного направления |
| **Субагенты-исполнители** | Ограниченная задача: код + тесты + правка доков в своей зоне | Ничего; изменения границ, архитектуры и публичных форматов — через ведущего разработчика |
| **Дежурный по релизу** | Сборки Windows/Linux/Web, прогон чек-листа §14.1, проверка адресов сервисов, запись результата в `docs/VERIFICATION.md` | Готовность релиза; остановка релиза при непройденном гейте |
| **Заказчик данных** (SMTP / домен / платежи) | Предоставляет почту, домен, аккаунт платёжного провайдера и доступы; подтверждает юридические тексты | Всё, что связано с реальными деньгами, персональными данными, внешними сервисами |

Разделение простое: **никто не согласует в одиночку то, что оплачивает или
раскрывает данные заказчика**, и никто не меняет серверную конфигурацию без явного
согласования (`SECURITY.md`, §шапка: «пока ничего не менять»).

## 5. Архитектурные правила (нормативные)

**5.1. Границы модулей: правило → запрет.**

| Правило | Запрещено |
|---|---|
| `packages/core` — чистый Dart, только stdlib; баррель без `dart:io` | Импортировать Flutter, `dart:io`/`dart:html` в `prepress_core.dart`; тянуть pub.dev-пакеты |
| Файловые операции домена — через `packages/core/lib/io.dart` (VM/desktop) | Импортировать `io.dart` из web-кода |
| UI вызывает домен и отображает результат | Дублировать доменную математику в `app/**`: «свои» формулы расхода/ТЭО |
| Сервис работает со своей БД и своим API | Читать/писать БД другого сервиса в обход API (`services/*/data`, тома `converter-data`, `auth-data`, `payments-data`) |
| Web-клиент — только относительные пути на единый origin | Зашивать адреса сервисов в web-код; включать CORS вместо прокси (`deploy/nginx/pp-web.conf`) |
| Desktop-адреса — через env `PP_*` | Хардкодить прод-адреса в новых местах; текущие дефолты — временная совместимость (§12, R5) |
| Платформенные различия — парой `*_io.dart` / `*_web.dart` за общим интерфейсом | Разветвлять поведение по платформе внутри экранов |
| Новый сервис обязан иметь: аутентификацию, лимиты частоты/размера, подпись вебхуков, healthcheck, запуск не от root | Публиковать маршрут без авторизации; принимать вебхук без проверки подписи |
| Pro-энфорсмент проверяется на сервере | Основывать денежные решения только на клиентском флаге (`app/state/entitlement.json`) |

Известные отклонения фиксируются честно, а не замалчиваются: конвертер без
авторизации и лимитов, открытые `/docs` и `/openapi.json`, `services/license` без
прод-развёртывания с константным секретом — `SECURITY.md` §2–3.

**5.2. Совместимость форматов.** Состояние проекта — JSON **v2**
(`app/lib/src/projects/project.dart:103`, `'schemaVersion': 2`); изменения только
**аддитивные** (новые поля необязательны, старые не удаляются и не меняют смысл).
Файлы с собственным форматом несут номер версии: библиотека материалов пишет
`'version': 1` и при чтении пропускает битые/неизвестные записи вместо падения
(`app/lib/src/materials/material_library.dart:166`, `:142–160`). Публичные
HTTP-контракты сервисов меняются по тому же правилу; ломающее изменение = новая
версия маршрута.

**5.3. Производительность и отзывчивость.** Тяжёлые операции (лечение, анализ,
раскрой, отчёты) на desktop идут через изолят: единая точка
`app/lib/platform/isolates.dart` → `heavy<T>()` (`isolates_io.dart` → `Isolate.run`).
На web изолятов нет: `isolates_web.dart` выполняет функцию на главном потоке — это
**известное ограничение** (гигантские файлы в браузере могут блокировать интерфейс);
новые тяжёлые операции на web обязаны резать работу на порции или выполняться на
сервисе. Ориентир скорости: лечение файла, занимавшее >90 с, после bbox-сеток
(`2f1513c`) уложилось примерно в 16 с (`docs/HANDOFF.md` §11); регресс по времени на
эталонном файле считается дефектом. Любой длительный шаг показывает статус и
попадает в журнал (`app/lib/src/logs/app_log.dart`).

## 7. Definition of Done

- [ ] **Код** внесён в правильный слой (§5.1); доменная математика не задублирована в UI.
- [ ] **Тесты**: есть проверка нового поведения либо объяснение, почему она невозможна; существующие тесты не ослаблены.
- [ ] **Документы** обновлены при изменении поведения: `README.md`, профильный README модуля, `РУКОВОДСТВО_ПОЛЬЗОВАТЕЛЯ.md` (если видно пользователю).
- [ ] **Гейты прогнаны** (§8) — приложен фактический вывод, а не пересказ.
- [ ] **Эталоны**: числа из §8 не изменились либо изменение обосновано и записано в `docs/VERIFICATION.md`.
- [ ] **Журналы**: значимое изменение отражено в `docs/HANDOFF.md`; факт приёмки — в `docs/VERIFICATION.md`.
- [ ] **Безопасность/деньги**: при затрагивании доступов, данных, платежей обновлён `SECURITY.md` либо добавлен риск в §12.
- [ ] **Чистота**: `git status --short` без артефактов и секретов.
- [ ] **Отправлено**: коммиты на русском, по одной теме, запушены в `origin/master`.

constant-time сравнение); opaque-токены 256 бит, в БД только sha256; лимит устройств
1/1; `logout` реально отзывает сессию; нет SQL-инъекций, `shell=True`/`os.system`,
path traversal и SSRF; web — единый origin через nginx, CORS выключен; пароли не
логируются; история git чиста от секретов.

**10.3. Обязательные требования для новых работ.** Новый сервис/маршрут — с

файл данных), требует согласования заказчика и записи в `SECURITY.md`. Приоритет:
**Фаза 1** из `SECURITY.md` §5 идёт первой, как только заказчик снимет запрет
«пока ничего не менять».

### 14.2. Порядок действий при инциденте

1. **Остановить распространение.** При подозрении на компрометацию: закрыть публичные порты, отозвать сессии, отключить проблемный сервис в `docker compose` — по согласованию с заказчиком, если затрагивается прод.
2. **Не чинить молча.** Никаких правок живого сервера без уведомления заказчика (`SECURITY.md`, §шапка).
3. **Зафиксировать факты.** Журналы (`docker compose logs`, журнал событий приложения), точные команды и вывод — без домыслов.
4. **Локализовать причину:** код приложения, сервис, конфигурация сервера, внешний сервис или действия пользователя.
5. **Оценить данные и деньги:** аккаунты, токены, файлы пользователей, заказы; были ли неправомерные списания или выдачи Pro.
6. **Устранить** через обычный процесс (§6): коммит, прогон гейтов (§8); при необходимости — внеплановый релиз с сокращённым чек-листом и явной пометкой о риске.
7. **Записать:** инцидент и выводы — в `SECURITY.md` (находка + статус) и `docs/VERIFICATION.md` (что проверено после исправления); при изменении правил — правка устава по §1.4.
8. **Предупредить пользователей**, если затронуты их данные или доступ: через руководство и, при наличии SMTP, письмом.
9. **Проверить повтор:** убедиться, что закрыт класс проблемы (тест/лимит/проверка), а не единичный симптом.
