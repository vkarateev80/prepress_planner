## 4. ОС Аврора: три варианта

Исходная точка: «ОС Аврора — открытый вопрос (порт/запуск)» (`docs/HANDOFF.md:294`).
Проверок на устройстве Авроры **не проводилось**; всё ниже — оценка вариантов, а не подтверждённые
факты. Технические возможности платформы (поддерживаемые версии браузера, наличие слоя
совместимости, доступные SDK) **требует проверки** у вендора/на тестовом устройстве.

| Вариант | Суть | Объём | Плюсы | Риски и открытые вопросы |
|---|---|---|---|---|
| **А. Web-версия в браузере Авроры** | Приложение уже собирается в web и работает через nginx единого origin (`docs/VERIFICATION.md:85`, `deploy/nginx/pp-web.conf`); платформенные вызовы в web изолированы (`app/lib/platform/*_web.dart`, `docs/HANDOFF.md:203-204`) | **S–M** | Минимальные затраты: переиспользуется существующая сборка и деплой; нет нового инструментального стека; обновления мгновенные (сервер) | Браузер и его версия на устройстве — **требует проверки** (движок/поддержка CanvasKit/WebGL); отсутствие офлайн-режима и локальных файловых операций (в web они через `save_out_web.dart`/`files_web.dart`); доступ к устройству ограничен; десктопный локальный конвертер (`app/lib/src/converter/converter_server.dart`) в web не работает — нужен сервер |
| **Б. Android APK через слой совместимости** | Собрать Android-сборку Flutter и запускать на Авроре через слой совместимости Android | **M–L** | Нативный запуск, интеграция с устройством; Flutter уже поддерживает Android-таргет из того же дерева | Нужен Android SDK и настройка таргета — **в репозитории Android-проекта нет ни в наличии, ни в проверках** (сборки только Windows/Linux/Web, `docs/VERIFICATION.md:87`); стабильность слоя совместимости и политика магазина Авроры — **требует проверки**; нужно отключить/переработать desktop-специфику (локальный сервер конвертера, пути `app/projects/`, env) |
| **В. Нативный Qt/Silica** | Отдельное приложение под Аврору с нативным UI | **XL** (отдельный проект) | Нативный UX, доступ к возможностям ОС, предсказуемая производительность | Домен написан на чистом Dart (`packages/core`, `docs/HANDOFF.md:193-195`) — порт математики на C++/Qt означает дублирование эталонной логики и риск расхождения с эталоном 9×5/5040/26.18/2032.0 (`packages/core/tool/e2e.dart:44-52`); потребуется отдельный SDK и команда; поддержка двух кодовых баз; целесообразность — **требует проверки** (объём рынка/требования заказчика) |

Рекомендация (не решение): начать с варианта **А** как проверки спроса (объём S–M, минимальный риск),
параллельно уточнить у вендора/заказчика требования к слою совместимости — и только затем принимать
решение по Б/В. Решение принимает заказчик; техническая проверка А на реальном устройстве —
обязательный первый шаг.

## 5. Правила обновления roadmap

1. **Один пункт — одна строка таблицы** с обязательными полями: «зачем», объём (S/M/L/XL),
   зависимости/блокеры, критерий готовности (проверяемый, а не «сделано»).
2. **Ничего не удалять.** Выполненный пункт переносится в раздел «Сделано» с датой, коммитом и
   ссылкой на приёмку (по образцу `docs/VERIFICATION.md`).
3. **Ссылки обязательны.** Каждый пункт ссылается на код/документ (`файл:строка`) либо явно
   помечается «требует проверки».
4. **Непроверенное — не утверждать.** Если прогона/факта нет, писать «требует проверки»
   (конвенция этого документа и `SECURITY.md`).
5. **Приоритет безопасности неприкосновенен.** Пункты §1 не понижаются и не удаляются, пока
   находки К-1…К-5 не закрыты и не подтверждены повторной проверкой (`SECURITY.md:50-64`).
6. **Блокеры фиксируются явно**: «нет домена/почты у заказчика» (`SECURITY.md:60-61`),
   «решение по license не принято» (`SECURITY.md:63`), «нет тестового устройства Авроры».
7. **Связь с чек-листами.** Изменение пункта, затрагивающего эксплуатацию/безопасность,
   синхронно отражается в `06_deploy_ops.md` §7–8 и `08_security.md` §4, §8.
8. **Дата и HEAD.** Каждое обновление — с датой и указанием HEAD коммита (сейчас `bed533e`);
   при расхождении документов правится тот, который отстал (прецедент 2026-09-07:
   `docs/HANDOFF.md` фиксировал `448dcba` — устранено блоком «Обновление после снимка»).
9. **Обновлять при каждом релизе/аудите** — сразу после обновления `docs/VERIFICATION.md`.
