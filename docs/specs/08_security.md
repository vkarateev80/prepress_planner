## 2. Нормативные требования

Формулировки «ДОЛЖНО/НЕ ДОЛЖНО» обязательны для новых работ; идентификаторы (Т-…) нужны для ссылок из задач и чек-листов.

### 2.1. Аутентификация и сессии

- **Т-1.** Аутентификация — только email+пароль; хеш пароля ДОЛЖЕН быть PBKDF2-SHA256 (не ниже 200 000 итераций) с индивидуальной солью и constant-time сравнением.
- **Т-2.** Сессии ДОЛЖНЫ быть серверными; клиенту выдаётся opaque-токен ≥256 бит, в БД — только его хеш (sha256); токен НЕ ДОЛЖЕН содержать полезной нагрузки.
- **Т-3.** Выход ДОЛЖЕН реально отзывать сессию; лимит устройств — 1/1; смена пароля ДОЛЖНА отзывать все сессии пользователя.
- **Т-4.** Срок сессии ДОЛЖЕН задаваться конфигурацией (`PP_TOKEN_TTL`) и быть обоснованным; просроченные сессии ДОЛЖНЫ удаляться фоновой чисткой.
- **Т-5.** Сброс пароля: код ДОЛЖЕН быть одноразовым, ≥8 символов (сейчас 6), с TTL; ответ `/auth/forgot` НЕ ДОЛЖЕН содержать код или признак наличия аккаунта — вне явного dev-флага он ДОЛЖЕН возвращать нейтральный ответ, а при неудаче отправки письма — 503.
- **Т-6.** Регистрация ДОЛЖНА требовать подтверждения email перед выдачей платных возможностей.
- **Т-7.** Ответы API НЕ ДОЛЖНЫ позволять перечислять аккаунты (различать email «есть/нет»).

### 2.2. Пароли

- **Т-8.** Минимальная политика пароля задаётся на сервере; пароль НЕ ДОЛЖЕН логироваться, возвращаться в ответах или попадать в отчёты об ошибках.
- **Т-9.** Смена/сброс пароля ДОЛЖНЫ инвалидировать текущие сессии и код сброса.

### 2.3. Лимиты (rate limiting)

- **Т-10.** ДОЛЖНЫ быть серверные лимиты по IP и по аккаунту для `/auth/login`, `/auth/register`, `/auth/forgot`, `/auth/reset` (попытки ввода кода) — с блокировкой/задержкой.
- **Т-11.** Конвертер ДОЛЖЕН ограничивать: число одновременных задач, размер файла **до** чтения тела, число задач на клиента/в час, время работы движка (timeout), память.
- **Т-12.** Ответы при превышении лимита — 429, без утечки деталей внутренней реализации.

### 2.4. Сетевые границы

- **Т-13.** Наружу публикуются ТОЛЬКО 22 (SSH, по ключу) и один веб-порт единого origin (`8081`, позже 443); порты 8120/8121/8122 НЕ ДОЛЖНЫ быть доступны из интернета — только внутри сети compose.
- **Т-14.** `/docs`, `/openapi.json`, `/redoc` и любые админ-маршруты ДОЛЖНЫ быть отключены или защищены аутентификацией в проде.
- **Т-15.** Статика данных (`/data`) НЕ ДОЛЖНА отдавать служебные каталоги (`work/`, `jobs/`), копии исходников и метаданные задач.
- **Т-16.** Firewall ДОЛЖЕН быть включён (ufw/iptables), fail2ban — установлен и настроен для SSH.
- **Т-17.** API, отдающий файлы пользователя, ДОЛЖЕН проверять право доступа к конкретному результату (сейчас `result_url` угадывается по `job_id` — доступ проверять обязательно).

### 2.5. TLS

- **Т-18.** Любой внешний трафик ДОЛЖЕН идти по HTTPS; http ДОЛЖЕН редиректиться на https. До появления домена внешние подключения десктопа к сервисам считаются недопустимыми.
- **Т-19.** Веб-статика ДОЛЖНА отдаваться с заголовками безопасности (CSP, `X-Content-Type-Options`, `Referrer-Policy`) и целостностью критичных ресурсов (SRI) либо запретом подмены (host-only CSP + контроль хешей артефактов).

### 2.6. Секреты и их хранение

- **Т-20.** Реальные `.env` НЕ ДОЛЖНЫ попадать в git; в репозитории — только `.env.example`.
- **Т-21.** Секреты ДОЛЖНЫ генерироваться криптостойко (`openssl rand -hex 32`) и храниться с правами `600`, владелец — сервисный пользователь.
- **Т-22.** Дефолтные/публичные секреты (`dev-secret-change-me`) НЕ ДОПУСКАЮТСЯ в проде; запуск с дефолтным секретом ДОЛЖЕН падать (fail-fast).
- **Т-23.** Секреты НЕ ДОЛЖНЫ передаваться в командной строке (видны в `ps`), в логах и в аргументах CI.

### 2.7. Права и контейнеры

- **Т-24.** Контейнеры ДОЛЖНЫ работать не от root (непривилегированный пользователь, read-only rootfs где возможно, `no-new-privileges`).
- **Т-25.** Права файлов стека: каталоги `755`, `.env` `600`; владелец — сервисный пользователь.
- **Т-26.** Базовые образы и версии зависимостей ДОЛЖНЫ быть зафиксированы (пиннинг); прод-зависимости НЕ ДОЛЖНЫ включать тестовые пакеты (`pytest`, `httpx`).

### 2.8. Платежи и подписки

- **Т-27.** Подтверждение оплаты ДОЛЖНО происходить только по подтверждённому событию провайдера (вебхук/серверный запрос), НЕ по клиентскому запросу.
- **Т-28.** Вебхук ДОЛЖЕН проверять подпись провайдера, иметь защиту от повторов (идемпотентность) и не принимать `order_id` без аутентичности события.
- **Т-29.** Энфорсмент Pro ДОЛЖЕН проверяться на сервере; клиентский `state/entitlement.json` НЕ МОЖЕТ быть источником истины.

### 2.9. Персональные данные и файлы пользователей

- **Т-30.** Хранить минимум: email, хеш пароля, сессии, заказы; пароли/коды — только в виде необратимых (или с солью) хешей.
- **Т-31.** Файлы пользователей — временные: удаляться по TTL; доступ к копии в `work/` закрыт; исходники не используются для иных целей.
- **Т-32.** Отчёты и выгрузки не ДОЛЖНЫ содержать секретов/токенов; имена файлов и пути не ДОЛЖНЫ ломать файловую систему (проверки path traversal/SSRF — обязательны в новых ручках).
- **Т-33.** Удаление аккаунта по запросу пользователя ДОЛЖНО удалять его данные (процедуры на дату нет).

### 2.10. Логирование

- **Т-34.** НЕ ДОЛЖНЫ логироваться: пароли, коды сброса, токены сессий, содержимое `.env`, SMTP-пароль, содержимое файлов пользователя.
- **Т-35.** В логи ДОЛЖНЫ попадать: время, сервис, событие (вход/отказ/лимит/ошибка), субъект (без токена), код ответа; логи не ДОЛЖНЫ отдаваться наружу.
- **Т-36.** Тексты исключений внутренних сервисов НЕ ДОЛЖНЫ уходить клиенту в неизменном виде.

### 2.11. Зависимости

- **Т-37.** Зависимости ДОЛЖНЫ быть закреплены по версиям; обновления — плановые, с прогоном тестов (`docs/specs/07_testing_quality.md` §6).
- **Т-38.** ОС и базовые образы ДОЛЖНЫ обновляться в рамках регламента (на 2026-09-07 — 317 необновлённых пакетов, `SECURITY.md:29`).

### 2.12. Реагирование и ротация

- **Т-39.** ДОЛЖЕН существовать порядок реагирования на инцидент (§6) и порядок ротации секретов (§7), включая отзыв сессий.
- **Т-40.** Любое изменение серверной конфигурации — только с фиксацией в журнале и после согласования с заказчиком (`docs/HANDOFF.md:236-239`).

## 5. Логирование: что можно и что нельзя

| Нельзя логировать (Т-34) | Можно логировать (Т-35) |
|---|---|
| Пароли и их хеши | Событие `login_failed` (email-хеш или без email) |
| Коды сброса (`dev_code`), содержимое писем | Время, сервис, эндпоинт, код ответа |
| Токены сессий, заголовки `Authorization` | `user_id`/`sub` (без токена), `device_id` |
| Содержимое `.env`, `PP_AUTH_SECRET`, SMTP-пароль | Факт срабатывания лимита (429) и источник запроса |
| Содержимое файлов пользователя | Размер файла, расширение, `job_id`, длительность |
| Полные тексты исключений движков (и клиенту тоже) | Внутренний код ошибки + корреляционный id |

Текущее состояние: пароли не логируются (`SECURITY.md:47`); централизованного сбора логов, ротации и маскировки нет (`deploy/README.md:114` — только `docker compose logs`).

## 6. Процедура реагирования на инцидент (требует внедрения)

Процедуры в репозитории нет (`SECURITY.md` фиксирует находки и план, но не регламент). Ниже — минимальный обязательный порядок (нормативная часть Т-39):

1. **Обнаружение.** Источники: аудит `SECURITY.md`, `docker compose logs`, всплеск 4xx/5xx, сообщения пользователей, внешнее уведомление.
2. **Фиксация.** Записать время, сервис, эндпоинт, `job_id`/`user_id`; снять состояние до изменений: `cd /stack/deploy && docker compose ps` и `docker compose logs --tail=500` (`deploy/README.md:114`).
3. **Локализация (без разрушения доказательств).** При активной эксплуатации закрыть вектор: остановить публикацию порта/сервиса, при необходимости `ufw deny` — после согласования (`docs/HANDOFF.md:236-239`).
4. **Отзыв доступа.** Сессии — через сброс пароля (удаляет `sessions`, `services/auth/auth_app/main.py:422-427`) или `logout`; SSH-ключи и пароль root — §7.
5. **Устранение.** Правка по плану §4 с прогоном гейтов `docs/specs/07_testing_quality.md` §6.
6. **Восстановление.** Данные — из бэкапа томов (`docs/specs/06_deploy_ops.md` §3.5); откат версии — §3.6 там же.
7. **Разбор.** Обновить `SECURITY.md` (новая находка с идентификатором) и при необходимости этот документ; зафиксировать в журнале проекта (`docs/HANDOFF.md:265-269`).
8. **Проверка.** Повторный аудит сценария + прод-пробы (`deploy/README.md:104-114`).

## 7. Ротация секретов (требует внедрения)

| Секрет | Когда ротировать | Как (на дату) |
|---|---|---|
| Пароль root SSH | Немедленно (не менялся — `SECURITY.md:18`), далее планово | По регламенту Фазы 1.2; после перехода на ключи пароль отключить |
| SSH-ключ `pp_vps_ed25519` | При подозрении на компрометацию/увольнении носителя | Заменить ключ, удалить старый из `authorized_keys` (`docs/HANDOFF.md:235-239`) |
| `PP_AUTH_SECRET` | По регламенту (например, раз в год) и при подозрении на утечку | Перегенерировать `openssl rand -hex 32` в `/stack/deploy/.env`, затем поднять стек (`deploy/install_new_server.sh:33-36,45-47`) |
| SMTP-пароль | При появлении SMTP и далее планово | Правка `.env` + перезапуск auth; в репозиторий не попадает (`.gitignore:51-53`) |
| Секрет license-сервиса (`dev-secret-change-me`) | Не применимо в проде (сервис не развёрнут) | `services/license/README.md:13-15` |

**Важно (требует проверки):** `PP_AUTH_SECRET` не используется для подписи токенов (`services/auth/README.md:47`) — его ротация **не отзывает сессии**. Отзыв выполняется сбросом пароля (удаление строк `sessions`, `services/auth/auth_app/main.py:422-427`) или 1/1-вытеснением при новом входе (`services/auth/README.md:8-9`); регламент «ротация = отзыв» нужно описать явно.
